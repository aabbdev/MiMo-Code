Answer a question about a payload that is TOO LARGE FOR THE MODEL'S CONTEXT WINDOW.

Read this first, because it decides whether to use this tool at all: if the payload fits in your window, reading it directly is cheaper, faster and at least as accurate. Measured on a 2.3 MB tree, ingesting it cost $0.177 and 28 s and covered more files than this tool did at $0.214 and 61 s. This tool exists for the payload that CANNOT be read — past the window there is no competition, because a direct request is rejected outright (a 6.8 MB tree resolves to 1.73 M tokens against a 1.05 M window).

It runs a Recursive Language Model loop (arXiv 2512.24601) with self-reflective program search (arXiv 2603.15653). The payload is loaded into persistent sandboxed JavaScript REPLs as `context` and `context_parts`; several independent trajectories are sampled in parallel, each writing code to slice and aggregate the payload and calling `llm_query` / `llm_query_batched` to ask questions of chunks. Only a truncated prefix of what a REPL prints returns to the model, so the payload never enters any context window. The trajectories are then compared by their own verbalized confidence and reasoning length, and the most confident-and-concise one is returned.

Do NOT use it for a payload you can simply read — `read` and `grep` are better in every way below the window.

ONE SHOT ONLY. Each call runs its own closed loop — its own system prompt and iteration history, re-sent at every step — and discards its kernel when it answers. Measured on two questions about the same 4.9 MB tree, both figures read from the session's own cost total: two calls cost $0.174 and 223 s, where loading the payload once with `repl` and iterating in the agent's own context cost $0.078 and 66 s. That 2.2x difference is the closed loops' overhead, not the payload being read twice: a second call here does read less when the question is narrower, and still costs more than twice what the same question costs in a live session.

Bounded on five axes, all reported: candidates, iterations, sub-calls, characters sent to sub-models, and total wall-clock time (30 minutes). The dollars are reported too, and charged to the session — a sub-call is a model call the session's own usage never contained, so `cost_usd` here is the only place it shows.

RECURSION IS OFF BY DEFAULT, AND MEASURED UNUSED. `depth: 2` offers the trajectories `rlm_query(text, question)`, a whole nested RLM over a sub-context. Measured once at depth 2 on a 4.9 MB tree with a query that contained a nested sub-problem: 0 nested calls over 8 iterations, and $0.293 for less work than the depth-1 runs did. It spends the trajectories' SAME sub-call budget, so it cannot multiply the bill — but raise the depth only if you specifically want that option, not to buy depth.
