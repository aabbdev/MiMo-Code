Externalize a payload into a persistent kernel and work on it there, so that a context far too large to read never has to enter your window.

`load` puts a file, a directory, or several trees into the kernel as the variables `context` (the whole payload as one string), `context_parts` (an array, one entry per file, or `name#2` when a large file was split further) and `context_part_names`. **It returns metadata only** — size, part count, and a short prefix — so loading a 5 MB tree costs a few hundred tokens instead of a million. The payload is then yours to search, slice and aggregate with code.

`code` runs JavaScript against those variables in the same kernel, and the variables you create survive to the next call. What your code prints comes back **TRUNCATED to a short prefix**, deliberately: printing a file does not put it in front of you and does not count as reading it. Code can tell you a file's name, size and structure; only `llm_query` can tell you what it MEANS. So route every question of meaning through the sub-LLMs, and use `context_parts` as the unit of work — pack several parts into each call, because the budget counts CALLS while a sub-LLM takes far more than one file.

`llm_query(prompt)` asks a sub-LLM; `llm_query_batched(prompts)` asks many at once with bounded concurrency. Both spend from a budget established by `load` (sub-calls and total characters), and both refuse with a message telling you what to do when it runs out. `reset` drops the kernel and frees its memory at once.

**Code for structure, sub-LLMs for meaning.** Searching, counting, locating, comparing sizes and slicing are free — the payload is a variable and does not cost tokens to inspect. What costs is meaning: reading what a piece of text *says*. Keep the two apart, and never present a structural fact as if it were a semantic one: knowing that a file is 4 000 characters long is not knowing what it does, and describing it anyway is an invention. An admitted gap is worth more than a confident guess.

**Before reading anything, screen.** `screen(question)` makes ONE cheap pass over short previews of every part and returns the indices worth reading — on a 462-part payload that is a fraction of the cost of reading it. Then read only those, and use the returned indices as `context_parts[i]`. Skipping the screen is what makes a loop expensive: reading everything to answer one question is the failure mode this exists to prevent. Screen again with a different question when the first pass does not find what you need.

For a follow-up question about a part you already asked about, use `ask_about(index, question)` rather than `llm_query`: it puts the part first and your question last, so the provider can serve the part from its cache instead of charging for it again.

Your OWN tools are reachable from inside the kernel as `tools.<name>(args)` — `await tools.read({ file_path: "src/x.cpp" })`, `await tools.grep({ pattern: "..." })` — through the same permission pipeline as calling them directly, so nothing is authorized twice or bypassed. `ALL_TOOLS` lists the names available in this step, and a nested call counts against `max_tool_calls`. Use them when the payload is not the only thing you need: the kernel can pull in a file that was not part of the load, or search the tree, without you having to leave the step.

ONE PAYLOAD, MANY QUESTIONS. The kernel outlives the call, so a second question about the same payload costs an iteration, not a reload: measured on two questions about the same 4.9 MB tree, loading once and answering both in the agent's own context cost $0.078 and 66 s from the session's own cost total. Ask everything you need about a payload before you `reset` it.

When to use it: when the payload cannot be read — past the model's context window. Below the window, reading is cheaper, faster and at least as accurate; measured on a 2.3 MB tree, ingesting it cost $0.177 and 28 s against $0.214 and 61 s for a loop, and covered more. Unlike a one-shot answer tool, this kernel is **yours for the session**: you keep every other tool while you work, and you iterate at your own pace.
